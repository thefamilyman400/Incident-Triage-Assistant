## Overview

This guide explains how IBM Bob transforms every incident into reusable Infrastructure-as-Code,
closing the loop from **alert → triage → automated remediation → prevention**.

The system moves from passive knowledge retrieval to active infrastructure automation:

```
Alert fires
    │
    ▼
Bob triages (RAG + runbook retrieval)
    │
    ▼
Bob plans investigation (branching workflow)
    │
    ▼
Root cause identified
    │
    ▼
Bob generates IaC templates
    │   ├── Shell triage script
    │   ├── Ansible remediation playbook
    │   ├── Terraform resource fix
    │   ├── Kubernetes manifest update
    │   └── Prometheus alert rule (monitoring-as-code)
    │
    ▼
Engineer reviews & applies templates
    │
    ▼
Bob generates post-mortem report
    │
    ▼
Bob authors new runbook → auto-indexed into knowledge base
    │
    ▼
Future incidents benefit from this knowledge
```

## The 5 Automation Outputs Bob Produces

### 1. Shell Triage Script (`triage_<type>.sh`)

A runnable bash script that automates the immediate triage steps from the runbook.

**Designed for:**
- Manual first response by on-call engineer (copy and run)
- Alert webhook automation (PagerDuty → script execution)
- Scheduled health checks (cron job)

**Example (High CPU):**
```bash
#!/bin/bash
# File: triage_high_cpu.sh
# Generated by IBM Bob — DO NOT EDIT manually

HOST=${1:-localhost}
THRESHOLD=90

echo "=== CPU Triage: $HOST ==="
echo "Top processes:"
ssh "$HOST" "ps aux --sort=-%cpu | head -10"

echo "Load average:"
ssh "$HOST" "uptime"

echo "Recent OOM events:"
ssh "$HOST" "dmesg | grep -i 'oom\|killed' | tail -5"
```

### 2. Ansible Playbook (`fix_<type>.yml`)

An Ansible play that runs the remediation across multiple servers simultaneously.

**Designed for:**
- Multi-server remediation (no SSH loop needed)
- Idempotent fixes (safe to re-run)
- Automated recovery workflows

**Example (Disk Space):**
```yaml
# File: fix_disk_space.yml
# Generated by IBM Bob
---
- name: Disk Space Remediation
  hosts: "{{ target_hosts | default('prod_servers') }}"
  become: yes
  tasks:
    - name: Remove logs older than 7 days
      find:
        paths: /var/log
        age: 7d
        recurse: yes
      register: old_logs

    - name: Delete old log files
      file:
        path: "{{ item.path }}"
        state: absent
      loop: "{{ old_logs.files }}"

    - name: Verify disk usage
      command: df -h /var/log
      register: disk_check
      changed_when: false

    - name: Report disk usage
      debug:
        msg: "{{ disk_check.stdout }}"
```

### 3. Terraform Resource Fix (`fix_<type>.tf`)

A Terraform block that corrects the infrastructure configuration to prevent recurrence.

**Designed for:**
- Permanent infrastructure changes
- Version-controlled IaC repositories
- PR-based review before applying

**Example (CPU — auto-scaling):**
```hcl
# File: fix_high_cpu.tf
# Generated by IBM Bob

resource "aws_autoscaling_policy" "cpu_scale_up" {
  name                   = "prod-db-cpu-scale-up"
  autoscaling_group_name = var.asg_name
  adjustment_type        = "ChangeInCapacity"
  scaling_adjustment     = 1
  cooldown               = 300
}

resource "aws_cloudwatch_metric_alarm" "high_cpu" {
  alarm_name          = "prod-db-high-cpu"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 2
  metric_name         = "CPUUtilization"
  namespace           = "AWS/EC2"
  period              = 120
  statistic           = "Average"
  threshold           = 90
  alarm_actions       = [aws_autoscaling_policy.cpu_scale_up.arn]
}
```

### 4. Kubernetes Manifest (`fix_<type>.yaml`)

A corrected K8s manifest that adjusts resource limits, adds HPA, or fixes deployment config.

**Designed for:**
- Kubernetes workload incidents
- Resource limit violations
- Deployment rollback or config correction

**Example (Service Down — resource limits):**
```yaml
# File: fix_service_down.yaml
# Generated by IBM Bob
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout-service
  namespace: production
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: checkout
        resources:
          requests:
            cpu: "250m"
            memory: "256Mi"
          limits:
            cpu: "500m"
            memory: "512Mi"
        env:
        - name: DB_POOL_SIZE
          value: "10"
        - name: DB_POOL_TIMEOUT
          value: "30"
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: checkout-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: checkout-service
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

### 5. Prometheus Alert Rule (`alert_<type>.yml`)

A monitoring-as-code rule that would have caught the incident earlier with better alerting.

**Designed for:**
- Catching incidents before they become P1
- Lowering alert thresholds based on incident learnings
- Adding missing coverage discovered during triage

**Example (High CPU):**
```yaml
# File: alert_high_cpu.yml
# Generated by IBM Bob
groups:
- name: infrastructure.cpu
  rules:
  - alert: HighCPUUsage
    expr: 100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 85
    for: 5m
    labels:
      severity: warning
      team: infrastructure
    annotations:
      summary: "High CPU usage on {{ $labels.instance }}"
      description: "CPU usage is {{ $value | humanize }}% — check for runaway processes."
      runbook: "runbooks/HIGH_CPU_RUNBOOK.md"

  - alert: CriticalCPUUsage
    expr: 100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 95
    for: 2m
    labels:
      severity: critical
      team: infrastructure
    annotations:
      summary: "CRITICAL CPU on {{ $labels.instance }}"
      description: "CPU at {{ $value | humanize }}% — immediate action required."
      runbook: "runbooks/HIGH_CPU_RUNBOOK.md"
```

## How to Use the IaC Features in the UI

### Generate Fix (from a triage response)
1. Ask any triage question (e.g. `CPU usage on prod-db-01 is at 98%`)
2. In the sources bar at the bottom of Bob's response, click **Generate Fix**
3. The IaC modal opens with all 5 template types
4. Click **Copy All** to copy the full output, or use the individual code block copy buttons

### Plan Investigation (from a triage response)
1. Click **Plan Investigation** in the sources bar
2. Bob produces a numbered workflow with conditional branches
3. Follow the workflow steps sequentially; each step has the exact command to run

### Save as Runbook (from the report modal)
1. After a full triage conversation, click **Generate Report**
2. Review the post-mortem
3. Click **Save as Runbook** — Bob generates a structured runbook `.md` and indexes it
4. The document count in the header increments — it is immediately queryable

### Welcome Screen Shortcuts
- Click **GENERATE IaC FIX** card to go directly to IaC templates for a CPU alert
- Click **PLAN INVESTIGATION** card to go directly to a branching workflow

## The Continuous Learning Loop

Every resolved incident improves the knowledge base automatically:

```
Incident resolved
    │
    ▼
Engineer clicks "Generate Report" → post-mortem generated
    │
    ▼
Engineer clicks "Save as Runbook" → runbook .md generated
    │
    ▼
POST /upload triggered automatically → file saved to runbooks/
    │
    ▼
Vector index rebuilt → new document immediately searchable
    │
    ▼
Next engineer facing the same alert gets the new runbook
```

**Result:** The more incidents are resolved through this system, the better it gets.
No manual documentation work required.

## API Reference for IaC Endpoints

### `POST /generate/iac`
Generates all 5 IaC template types for the given incident.

**Request:**
```json
{
  "query": "CPU usage on prod-db-01 is at 98% for the last 12 minutes",
  "conversation": "USER: CPU usage...\nASSISTANT: ## Immediate Actions..."
}
```

**Response:**
```json
{
  "iac": "## IaC Remediation Templates\n\n### Shell Automation Script\n...",
  "sources": ["runbooks/HIGH_CPU_RUNBOOK.md", "incidents/INC-2847-HIGH-CPU-BATCH-JOB.md"]
}
```

---

### `POST /generate/runbook`
Generates a complete runbook `.md` document from a resolved incident conversation.

**Request:**
```json
{
  "query": "CPU usage on prod-db-01 is at 98%",
  "conversation": "full triage conversation text"
}
```

**Response:**
```json
{
  "runbook": "# HIGH CPU ALERT Runbook\n\n## Overview\n..."
}
```

---

### `POST /orchestrate`
Generates a structured investigation workflow with conditional branching.

**Request:**
```json
{
  "query": "CPU usage on prod-db-01 is at 98%",
  "history": [{"role": "user", "text": "previous message"}]
}
```

**Response:**
```json
{
  "workflow": "## Incident Classification\n...",
  "sources": ["runbooks/HIGH_CPU_RUNBOOK.md"],
  "severity": "P2"
}
```
